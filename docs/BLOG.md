# 我审计了自己的评分器，然后撤回了自己的结论

> 一个 RAG 项目里，最值钱的东西不是检索，是**证明检索有用**的那套测量。
> 这篇文章讲三次翻车：rubric 换版把分数打崩、样本翻 3 倍后结论变强、以及一个
> 「看起来很漂亮」的检索指标其实是恒等式。

项目地址：`github.com/zaxiu88888/issue-rag`（Vite issue tracker 上的检索增强问答）

---

## 一、先说结论

在 `vitejs/vite` 上，用 **95 条人工复核**的问题（真实 issue 标题当查询、维护者回复当参考答案）：

| | 闭卷（无检索） | 检索（最好配置） |
|---|---|---|
| 判对 | 8.4% | 64.2% |
| 加权准确率 | 0.221 | 0.700 |
| 被判为编造 | 1.1% | 20.0% |

检索确实有用。但**增益有多大取决于谁来判**：

- 用项目内判分器（`deepseek-chat`）：**3.2×**
- 换更严格的独立判分器（`deepseek-reasoner`）：**2.3×**
- 30 条人工盲评：**5.2×**

也就是说**机器测出来的是下界**。这跟「LLM 判分器会吹高分数」的常见担心方向相反。

而四种检索配置（BM25 / dense / hybrid / hybrid+rerank）之间，**无法区分**。
这不是没测，而是测了之后发现差异落在噪声带里。

---

## 二、翻车一：让判分器更可复现，结果更糟

最初的判分器很简单：给模型问题、参考答案、候选答案，让它直接说 `correct` / `partial` / `incorrect`。

问题是一致性差：同一个模型跑两遍，有 7–29% 的条目判定不同，而且分歧集中在
`partial` / `incorrect` 边界上——恰好是「整体判断」这种提示词没有定义的地方。

于是我做了工程上最自然的动作：**把这个决定从模型手里拿走**。模型只回答四个事实性问题：

1. `states_resolution`：候选是否给出了与参考相同的解法？
2. `generic_advice_only`：候选是否只包含「清缓存 / 升级 Node / 看文档 / 给个最小复现」这类对任何项目都成立的话？
3. `wrong_specific`：候选是否给出了与参考**冲突**的版本号或 issue 号？
4. `contradicts`：候选是否断言了参考否定的事？

判定由代码映射，模型不再有机会「感觉」。

它奏效了——一致率从 **82.8% 升到 93.1%**。

然后分数崩了：

| rubric | closed_book | hybrid+rerank | 一致率 |
|---|---|---|---|
| ① 整体判断 | 0.336 | 0.517 | 82.8% |
| ② 四个检查（`wrong_specific` = 「参考里没有的细节」） | **0.034** | **0.259** | **93.1%** |
| ③ 四个检查（`wrong_specific` = 「与参考冲突的版本号/issue 号」） | 0.287 | **0.562** | 82.1% |

原因在第 3 个检查的定义上：「**不在参考答案里**」被我当成了「**编造**」。
而检索答案天然会引用**其他摘录**里的细节——那正是检索的价值。结果 97% 的闭卷答案、
93% 的检索答案被标成编造。

把检查收窄到「与参考冲突的版本号或 issue 号」之后，一切回来了，而且跑间差从
0.069 降到 0.018（降了 3.8 倍）。

### 这个教训比结果重要

**判分器的「更好」不是一致率。** 是三件事同时看：

1. 你报告的那个数字的**跑间差**
2. **水平值**本身
3. **哪个子问题被触发**（可审计性）

臂 ② 赢了第 1 项，输了第 2、3 项。只盯一致率的我会把它发出去。

一句诚实的补充：臂 ③ **没有**提高逐条一致率（82.1% vs 82.8%）。它改善的是两遍之间的
**净偏移**——误差互相抵消，而不是偏置在聚合值上。既然公开的都是聚合值，那才是要紧的方差。

## 三、翻车二：扩样本，然后主效应变强了

评测集从 29 条扩到 95 条（语料 3,078 → 5,473 篇，窗口拉到 18 个月，200 条候选逐条人工复核，
保留 47.5%）。

常见的担心是「小样本让效应虚高，样本一大就回归」。实际结果相反：

| 系统 | 29 条 | 95 条 | Δ |
|---|---|---|---|
| closed_book | 0.190 | 0.221 | **+0.031** |
| bm25 | 0.517 | 0.700 | +0.183 |
| dense | 0.466 | 0.632 | +0.166 |
| hybrid | 0.500 | 0.695 | +0.195 |
| hybrid+rerank | 0.500 | 0.679 | +0.179 |
| **增益** | **2.72×** | **3.17×** | +0.45× |

**对照组几乎没动（+0.031），实验组动了 0.18。** 这是我想要的结果，而且很少有项目去检查它。

但有一点必须说清楚：**绝对数字不能跨版本比较**。更宽的窗口补进来大量「问题被明确解决」的
近期线程，检索从中获益远大于闭卷。所以 29 条那版 README 里的数字现在是历史，不是现状。

## 四、翻车三：那张漂亮的检索指标是恒等式

这是最值得讲的一次，因为它一开始看起来是**好消息**。

我的检索表长这样（四个检索器，一模一样）：

| retriever | recall@5 | recall@5 留一 | MRR | MRR 留一 |
|---|---|---|---|---|
| bm25 | 1.000 | 0.000 | 1.000 | 0.000 |
| dense | 1.000 | 0.000 | 1.000 | 0.000 |
| hybrid | 1.000 | 0.000 | 1.000 | 0.000 |
| hybrid+rerank | 1.000 | 0.000 | 1.000 | 0.000 |

**1.000 的 recall 和 MRR**，而且**留一交叉全是 0**。我一开始以为是我构造得「太难」，
还怀疑过是语料放大导致的。后来翻了归档臂才发现：**29 条那几轮的数字逐位相同**——
它从来没变过。

两个原因，性质不同：

1. **`recall@5 = MRR = 1.0` 是构造性的。** 查询就是 issue 标题，而语料每个 chunk 都带
   标题前缀，所以金标 issue 必然排第 1。实测**检索窗口里 98–99.8% 都是金标 issue
   自己的 chunk**——检索器找到线程后，五个槽位全被同一线程填满。
2. **`留一交叉 ≡ 0` 是定义性的。** 参考文档就是金标 issue 里那条评论，把它从索引里
   拿掉后，唯一相关文档按定义消失了。它恒为 0 不是经验发现，是恒等式。

### 换一个真能区分的指标

把「相关」从 issue 改成**回答的那条评论**：

| retriever | gold chunk@5 | gold chunk MRR | top-1 | 窗口里来自同一 issue |
|---|---|---|---|---|
| bm25 | 0.611 | 0.280 | 0.116 | 0.983 |
| dense | 0.516 | 0.206 | 0.063 | 0.998 |
| hybrid | 0.579 | 0.247 | 0.084 | 0.996 |
| hybrid+rerank | **0.621** | **0.289** | **0.147** | 0.990 |

这张表有区分度了——它能把 dense（0.516）和 reranker（0.621）分开。

然后冒出一个更有意思的反面结果：**检索质量最好的那个，答案不是最好的。**
reranker 检索到回答评论的比例最高（0.621），端到端却落后于 BM25（0.679 vs 0.700）。

**更好的检索不等于更好的答案。** 生成器怎么用这个窗口，比检索质量的最后一点增量更重要。

## 五、人工盲评：机器低估了机器的效果

四轴审计的最后一轴，也是唯一不是「模型判模型」的一轴：30 条答案（每系统 15 条），
通过本地盲评页判定——评审只看到问题、参考答案、候选答案，看不到判定、看不到来源系统。

| 指标 | 值 |
|---|---|
| 完全一致 | **70.0%** |
| 可用/不可用一致 | 73.3% |
| 二次加权 κ | **0.816**（almost perfect） |

| 系统 | n | 人工均分 | 判分器均分 |
|---|---|---|---|
| closed_book | 15 | **0.167** | 0.267 |
| hybrid+rerank | 15 | **0.867** | 0.733 |

最后两列是结论：**判分器对泛泛建议手松（+0.100），对好答案手紧（−0.133）**。
人看到的差距是 +0.700（5.2×），判分器只看到 +0.466（2.75×）。

本来保留条件要自己先说：一位评审、每系统 15 条、一次坐下来评完。它验证方向，不验证小数位。
但它和「扩样本后增益变大」指向同一方向，两个独立检查都说实测增益是地板。

## 六、最后，能站住的只有两条

| 主张 | 判定 |
|---|---|
| 检索优于闭卷 | **成立**——每个 rubric、每个判分器、每一遍、每种样本量、人工盲评 |
| 增益是「4 倍」 | **不成立**——2.3×–3.2×（人工样本约 5×） |
| rerank 是最好的检索配置 | **不成立**——换判分器排序就翻转，差 0.03 |
| 四种配置之间的排序 | **未决**——落在噪声带里（跑间差 0.005–0.026） |
| 判分器低估了增益 | **支持**——+0.100 / −0.133 |
| 评测集太小、不可信 | **不成立**——扩 3.3 倍，对照组只动 0.031 |

四条独立证据都说「别主张排序」：散布只有 0.07；跑间噪声 0.005–0.026；换判分器排序翻转；
检索最好的那个答案不是最好。

---

## 七、如果你只记三句话

1. **可复现 ≠ 正确。** 把判分器调得更一致，可能只是把偏差调得更稳定。
2. **指标要能证伪。** 一个所有方法都拿 1.0 的指标，大概率是恒等式，不是好消息。
3. **对照组要跟着扩。** 样本翻 3 倍时，如果只有实验组动，那才是效应；如果两组都动，
   那是语料变了。

## 附：怎么复现

```bash
git clone https://github.com/zaxiu88888/issue-rag
cd issue-rag
python -m pip install -e .
echo "DEEPSEEK_API_KEY=sk-..." >> .env

python -m issue_rag.fetch issues   --preset vite --months 18
python -m issue_rag.fetch comments --preset vite --mode per-issue --max-comment-issues 300
python -m issue_rag.corpus  --preset vite
python -m issue_rag.evalset --preset vite       # 然后人工填 evalset_review.csv
python -m issue_rag.evalset --preset vite --finalize

python -m issue_rag.evaluate --preset vite --provider deepseek \
    --systems closed_book,bm25,dense,hybrid,hybrid_rerank
python -m issue_rag.evaluate --preset vite --provider deepseek --regrade \
    --judge-model deepseek-reasoner --judge-max-tokens 6000 --run-tag reasoner
python -m issue_rag.sensitivity --preset vite --variant reasoner
```

所有数字都能由这些命令重新生成，`data/results/` 是它们的原始输出。仓库里没有手改的数字。
