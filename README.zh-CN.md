# issue-rag — 一个会测量自己的技术支持问答系统

[English](README.md) | **简体中文**

面向真实开源仓库 issue tracker 的检索增强问答系统（RAG），围绕一个问题设计：

> **大模型在讲一个快速迭代的库时，说错的比例到底有多高？把最近的 issue 检索进来能不能修好？**

多数 RAG demo 用断言回答前半句，然后跳过后半句。这个仓库交付的是**测量**：从维护者回答里挖出来的人工复核评测集、五组系统对照，以及一张每一行都是消融实验的结果表。

---

## 假设

快速迭代类库的支持流量，答案大多落在**最近六到十二个月的 issue** 里——哪个版本修了这个 bug、哪个 API 取代了已废弃的调用、为什么博客里的示例已经编译不过。

训练数据截止在这些 issue 之前的模型不可能知道这些。于是它做了语言模型最擅长的事：编一个像样的版本号、一个像样的 API 名，配一个笃定的语气。

这个失效模式是可测量的，也正是本项目测量的东西。在 `vitejs/vite` 上，用**95 条人工复核**的问题测得：

| | 闭卷（无检索） | 检索（最好配置） |
|---|---|---|
| 判定为 `correct` | 8.4% | **64.2%** |
| 加权准确率 | 0.221 | **0.700** |
| 被判为 `fabricated`（编造） | 1.1% | 20.0% |

检索明显有用——但**增益有多大取决于谁来判**，所以这里报区间而不是一个数：

- 项目内判分器（`deepseek-chat`）：**0.221 → 0.700**（3.2×）
- 换更严格的独立判分器（`deepseek-reasoner`）：**0.305 → 0.711**（2.3×）
- **人工盲评** 30 条：**0.167 → 0.867**（5.2×）

人工盲评是最有意思的一条：它与判分器的判定一致率 **70.0%**（二次加权 κ=0.816），但分歧方向一致——判分器对「泛泛建议」过宽（+0.100），对「真实答案」过严（−0.133）。**所以机器测出来的增益偏保守**，这跟通常对「LLM 判分不可靠」的担心方向恰好相反。

扩大样本本身就是一次实验，也照实报告。从 29 条扩到 95 条，闭卷只动了 **+0.031**，而四个检索系统都动了 +0.17~+0.20——**样本翻 3 倍后主效应变强了，而不是回归到零**。见 [29 条 vs 95 条](#29-条-vs-95-条扩大样本改变了什么)。

有两件事刻意**不主张**：四种检索配置之间无法区分（0.632–0.700，差距小于判分器自身噪声，而且换判分器排序就翻转）；以及检索会**抬高**编造率——这是本仓库最反直觉的结果。细节都在 [结果](#结果) 一节。

## 为什么这不是又一个「和你的 PDF 聊天」

三个决定做了差异化，而且三个都能在代码里核对：

**1. 评测集是从维护者回答里挖的，不是 LLM 生成的。** 每条问题的参考答案都是维护者在 issue 里真实说出的一句话。这排除了「模型自己出题自己答」的污染，也是零标注成本。

**2. 判分器的判定由代码映射，不由模型决定。** 模型只回答四个事实性子问题（是否给出解法、是否只有泛泛建议、是否编造了与参考冲突的版本号、是否与参考矛盾），verdict 由 `judge.verdict_from_checks` 在代码里映射。这让「为什么判 partial」可审计，而不依赖一次采样。

**3. 判分器本身被审了四个轴。** 换判分模型、同模型跑两遍、换 rubric 版本、以及人工盲评。第三个轴的第一次尝试还翻了车（可复现性升到 93%，分数却崩了），这件事被完整记在 [rubric 那一节](#rubric-本身也是一次实验)。

## 结果

> 由 `python -m issue_rag.evaluate --preset vite --provider deepseek` 生成，
> 原始输出在 `data/results/`。**所有数字都不是手改的。**

配置：**95 条人工复核**问题，生成与判分都是 `deepseek-chat`，检索 5 段，语料
**5,473 篇**（来自 **771 个 issue、2,593 条评论**），rubric ③。

### 答案质量

| 系统 | accuracy | correct | partial | incorrect | fabricated | 带引用 | p50 | p95 |
|---|---|---|---|---|---|---|---|---|
| `closed_book`（无检索） | 0.221 | 8.4% | 27.4% | 64.2% | 1.1% | 0% | 4.32 s | 5.00 s |
| `bm25` | **0.700** | **64.2%** | 11.6% | 24.2% | 20.0% | 100% | 3.70 s | 4.29 s |
| `dense`（bge-base-en-v1.5） | 0.632 | 55.8% | 14.7% | 29.5% | 28.4% | 100% | 3.65 s | 4.29 s |
| `hybrid`（RRF） | 0.695 | 63.2% | 12.6% | 24.2% | 21.1% | 100% | 3.53 s | 4.19 s |
| `hybrid + rerank`（bge-reranker-base） | 0.679 | 62.1% | 11.6% | 26.3% | 23.2% | 100% | 3.77 s | 4.33 s |

_accuracy = correct(1.0) + partial(0.5)；fabricated = 判分器标记出错误的版本号、API 或文件路径。每行 n=95，0 次调用失败。_

**检索把准确率从 0.221 抬到约 0.70，而四种检索配置之间无法区分**（0.632–0.700，差距小于判分器自身噪声）。后半句和前半句一样重要：本 README 曾经主张「rerank 最好」，在最终 rubric 下这个主张不成立——见 [哪些结论站得住](#哪些结论站得住哪些站不住)。

### 29 条 vs 95 条：扩大样本改变了什么

上一版 README 报告的是 29 条。这版把窗口拉到 18 个月（语料 3,078 → 5,473 篇）并逐条重审：200 条候选，保留 95 条，丢弃 105 条。同一 rubric、同一生成器、同一条命令。

| 系统 | 29 条 | 95 条 | Δ |
|---|---|---|---|
| `closed_book` | 0.190 | 0.221 | **+0.031** |
| `bm25` | 0.517 | 0.700 | +0.183 |
| `dense` | 0.466 | 0.632 | +0.166 |
| `hybrid` | 0.500 | 0.695 | +0.195 |
| `hybrid + rerank` | 0.500 | 0.679 | +0.179 |
| **增益（最好检索 ÷ 闭卷）** | **2.72×** | **3.17×** | +0.45× |

两种读法，都诚实：

1. **主结论稳定，而且变强了。** 样本大 3.3 倍，闭卷只动 3 个点；检索动了约 0.18。一个在样本翻 3 倍后**反而变大**的效应，不太可能是小样本假象。
2. **绝对数字不能跨版本比较。** 更宽的窗口补进来大量「问题被明确解决」的近期线程，检索从中获益远大于闭卷。不要拿这一页的某一行去和旧截图比。

置信区间也自然收窄：n=29 时一条样本动 3.4 个点，n=95 时动 1.1 个点。

### 这里面有多少是判分器的功劳？

三个问题，三次对照。所有对照都**复用同一批已存的答案**（`evaluate --regrade`），只换判分环节。

**a) rubric 影响多大？** 同模型、同答案，rubric ① vs ③（在**旧的 29 条**上测，因为重新实现 rubric ① 等于改动被测仪器，不混进当前跑批）：

| 系统 | rubric ① | rubric ③ | Δ |
|---|---|---|---|
| `closed_book` | 0.138 | 0.190 | +0.052 |
| `bm25` | 0.483 | 0.517 | +0.035 |
| `dense` | 0.448 | 0.466 | +0.017 |
| `hybrid` | 0.466 | 0.500 | +0.035 |
| `hybrid + rerank` | 0.586 | 0.500 | **−0.086** |

几乎每个系统只动几个百分点，只有 rerank 掉 −0.086——它当初「领先」的假象就是这么消失的。

**b) 换判分模型影响多大？** 同 rubric、同一批 95 条答案，`deepseek-chat` vs `deepseek-reasoner`：

| 系统 | `deepseek-chat` | `deepseek-reasoner` | Δ |
|---|---|---|---|
| `closed_book` | 0.221 | 0.305 | **+0.084** |
| `bm25` | 0.700 | 0.658 | −0.042 |
| `dense` | 0.632 | 0.595 | −0.037 |
| `hybrid` | 0.695 | 0.668 | −0.026 |
| `hybrid + rerank` | 0.679 | **0.711** | **+0.032** |
| **增益** | **3.17×** | **2.33×** | |

更严格的判分器对**闭卷答案宽松**、对**检索答案严格**，于是把增益压低了。它还把排序掀了：`deepseek-chat` 下 `bm25` 第一，`deepseek-reasoner` 下 `hybrid + rerank` 第一，而最大变动只有 0.042——落在下一项测出的噪声带里。

**c) 判分器和自己一致吗？** `deepseek-reasoner` 跑两遍、同一批 95 条答案（这是**噪声地板**：两个系统的差距小于它就不能当结论）：

| 系统 | 第一遍 | 第二遍 | Δ | 一致率 |
|---|---|---|---|---|
| `closed_book` | 0.305 | 0.289 | −0.016 | 78.9% |
| `bm25` | 0.658 | 0.668 | +0.011 | 86.3% |
| `dense` | 0.595 | 0.621 | +0.026 | 84.2% |
| `hybrid` | 0.668 | 0.684 | +0.016 | 86.3% |
| `hybrid + rerank` | 0.711 | 0.705 | −0.005 | 86.3% |

聚合值的跑间漂移是 **0.005–0.026**，而且两遍排序**完全一致**。跨判分器一致率更低（53.7%–83.2%），所以上面报的是区间，不是一个点。

**d) 人同意吗？** 全项目唯一不是「模型判模型」的测量。30 条答案（每个系统 15 条）通过本地盲评页判：评审只看到问题、参考答案、候选答案，**看不到判分器的判定，也看不到答案来自哪个系统**。

| 指标 | 值 |
|---|---|
| 评审条数 | 30 |
| 完全一致 | **70.0%** |
| 可用/不可用一致 | **73.3%** |
| 二次加权 κ | **0.816**（almost perfect） |

| 系统 | n | 完全一致 | 可用一致 | 人工均分 | 判分器均分 |
|---|---|---|---|---|---|
| `closed_book` | 15 | 67% | 73% | **0.167** | 0.267 |
| `hybrid + rerank` | 15 | 73% | 73% | **0.867** | 0.733 |

最后两列就是结论。**判分器对泛泛建议手松、对好答案手紧**：闭卷答案它给高 0.100，rerank 答案它给低 0.133。所以在这批样本上，人看到的差距是 **+0.700（5.2×）**，判分器只看到 +0.466（2.75×）——**机器测出来的是下界，不是虚高**。

必要的保留：一位评审、每系统 15 条、一次坐下来评完。把它当作「仪器方向对不对」的验证，不要当作精确估计。值得注意的是，这一轴和样本扩容那一轴指向同一个方向：实测的检索增益是地板。

### 哪些结论站得住，哪些站不住

| 主张 | 判定 |
|---|---|
| 检索优于闭卷 | **成立**——每个 rubric、每个判分器、每一遍、每种样本量、以及人工盲评 |
| 增益是「4 倍」 | **不成立**——模型判分给出 **2.3×–3.2×**，人工样本指向约 5× |
| rerank 是最好的检索配置 | **不成立**——`deepseek-reasoner` 下它第一，`deepseek-chat` 下落后于 `bm25`，差 0.03 |
| `bm25` / `hybrid` / `dense` / `rerank` 之间的排序 | **未决**——全部落在 0.07 内，等于在噪声带里 |
| 判分器低估了增益 | **支持**——对泛泛建议过宽 0.100，对检索过严 0.133 |
| 评测集太小、不可信 | **不成立**——扩了 3.3 倍，闭卷只动 0.031 |

排序那一行是有证据支撑的「未决」，不是偷懒：四个配置相差不超过 0.07；判分器自身跑间噪声 0.005–0.026；换判分器排序就翻转；issue 级检索指标是恒等式（见下）。四条独立证据同向。

### 只看闭卷答错的题（n=87）

| 系统 | accuracy | correct | partial | incorrect | fabricated |
|---|---|---|---|---|---|
| `closed_book` | 0.149 | 0.0% | 29.9% | 70.1% | 1.1% |
| `bm25` | 0.678 | 62.1% | 11.5% | 26.4% | 21.8% |
| `dense` | 0.621 | 54.0% | 16.1% | 29.9% | 28.7% |
| `hybrid` | 0.672 | 60.9% | 12.6% | 26.4% | 21.8% |
| `hybrid + rerank` | 0.672 | 60.9% | 12.6% | 26.4% | 24.1% |

这是同一次跑批的子集（n=87），不是筛过的评测集——上面那张表仍然算全部 95 条，所以这个对照没有做弊。检索的功力就在这里：模型本来就会的题它帮不上，而那类题只有 8/95。

### 检索质量——按「回答的那条评论」衡量，不是按 issue

这里的「相关」是**回答问题的评论**，不是它所在的整个线程：

| 检索器 | gold chunk@5 | gold chunk MRR | gold chunk top-1 | 窗口里来自同一 issue 的比例 |
|---|---|---|---|---|
| `bm25` | 0.611 | 0.280 | 0.116 | 0.983 |
| `dense` | 0.516 | 0.206 | 0.063 | 0.998 |
| `hybrid` | 0.579 | 0.247 | 0.084 | 0.996 |
| `hybrid + rerank` | **0.621** | **0.289** | **0.147** | 0.990 |

这张表**有区分度**——它能把 `dense`（0.516）和 reranker（0.621）分开，而答案质量表分不开。它还给出了本仓库最有意思的反面结果：**检索质量最好的那个，答案不是最好的**（`hybrid + rerank` 这里 0.621 领先，但端到端 0.679 落后于 `bm25` 的 0.700）。检索得更准，没有完全传导到最终答案——这才是「四种配置无法排序」背后诚实的原因。

最后一列解释了更早那张 issue 级表为什么失效：**检索窗口里 98–99.8% 都是金标 issue 自己的 chunk**。检索器先找到正确的线程（这是必然的——查询就是该线程的标题），然后把五个槽位全用该线程的 chunk 填满。所以任何「有没有检索到正确 issue」的指标，对每个检索器都恒为约 1.0。

### rubric 本身也是一次实验

上面的判分器是直接要一个 verdict。同模型跑两遍有 7–29% 的条目不一致，而且分歧集中在 partial/incorrect 的边界上——正是「整体判断」这种提示词没有定义的地方。于是判分器被改成回答四个事实性子问题，verdict 在代码里映射。

第一次尝试以一种很有教育意义的方式变得更糟。下面每个臂都是 `deepseek-reasoner` 在同一批已存答案上的两遍：

| rubric | closed_book | hybrid+rerank | rerank 跑间 Δ | rerank 一致率 |
|---|---|---|---|---|
| ① 整体判断（原始） | 0.336 | 0.517 | 0.069 | 82.8% |
| ② 四个检查，`wrong_specific` = 「任何不在参考答案里的细节」 | 0.034 | 0.259 | 0.069 | 93.1% |
| ③ 四个检查，`wrong_specific` = 「与参考矛盾的版本号/issue 号」 | 0.287 | **0.562** | **0.018** | 82.1% |

**臂 ② 是那个反面教材。** 它把一致率抬到 93%，同时把两个分数都打崩：因为「不在参考答案里」不等于「编造」——检索答案合理引用其他摘录里的细节，而过宽的检查把 97% 的闭卷答案、93% 的检索答案都标成了编造。**可复现存疑比有噪声但大致正确更糟。**

**臂 ③** 把检查收窄到只抓版本号和 issue 号，编造标记率降到 0%/19%，分数回来了，关键系统的跑间差也降到原来 1/3.8（0.069 → 0.018）。

一条诚实的限制：臂 ③ **没有**提高逐条一致率（82.1% vs 82.8%）。它改善的是两遍之间的**净偏移**——误差互相抵消，而不是偏置在聚合值上。既然这里报的每个数字都是聚合值，那才是真正要紧的方差。

### 五个值得注意的点

**1. reranker 的优势没扛过 rubric 修正。** rubric ① 下它领先 0.10；③ 下它与普通 hybrid 持平、落后 BM25。rubric 让它动 −0.086，其他系统只动 +0.02~+0.05。**一个在仪器被修正后就翻转的结果，是关于仪器的结果**——这是本仓库最有价值的自查。

**2. 四种检索配置无法区分。** 0.632、0.679、0.695、0.700——0.07 的散布，而判分器聚合跑间噪声是 0.005–0.026，换判分器排序还翻转。四条独立证据同向：散布小、排序跨判分器不稳定、issue 级检索指标是恒等式、检索最好的那个答案不是最好。**不要主张排序。**

**3. 检索买到的是 2.3×–3.2×，这是耐久结论。** 闭卷 0.221 抬到约 0.70，这个增益扛过了两个判分器（3.17× vs 2.33×）、一次 rubric 变更、3.3 倍样本扩容，而且在人工盲评下**更大**（约 5×）。不是「4 倍」，也不是 1.9 倍——样本变大时区间是**往上**走的，与通常的小样本乐观方向相反。

**4. 检索让模型「自信地错」而不是「诚实地不知道」。** 带检索时编造率 20–28%、引用标记 100% 出现；不带检索时模型多数承认不知道，编造率只有 1.1%。**Grounding 与引用保真是两个问题**，第二个在本项目没解决。

**5. 更好的检索不等于更好的答案。** reranker 检索到回答评论的次数最多（0.621 vs BM25 的 0.611），端到端却更低（0.679 vs 0.700）。生成器怎么用这个窗口，比检索质量的最后一点增量更重要——这也是为什么本仓库**同时**报检索表和答案表，从不从一个推另一个。

## 设计取舍

**检索单位 = 一条评论一个文档，前缀 issue 标题。** 维护者回复通常自包含（「v5 里先调 `convertToModelMessages`」），单独检索和引用都成立。标题前缀让 chunk 级引用可解释。

**查询 = issue 标题，不是 issue 正文。** 用正文会匹配到 issue 自身文本，抬高所有指标。标题也更接近用户真实输入。

**用 RRF 而不是分数归一化。** BM25 分数与余弦相似度不可比；百分位或 min-max 归一化对候选池大小敏感。倒数排名融合只用位置，让 hybrid 稳健、消融可解释。

**默认生成器是本地 3B 模型。** 小到能在 16 GB 笔记本 GPU 上跑，任何人都能在没有 API key 的情况下复现这张表。代价真实：绝对分数低于前沿模型。`--endpoint` 可以换任何 OpenAI 兼容服务，而闭卷 vs RAG 的**差距**才是结论——那个差距在更强的生成器下依然成立。

## 局限性

写在这里，因为一张没有局限性说明的结果表就是营销。

* **LLM 判分，但有人工校验。** 换判分器最多让一个系统动 0.084，同一判分器跑两遍最多动 0.026，换 rubric 让一个系统动 0.086。30 条盲评一致率 70.0%（κ=0.816），且分歧方向一致：对泛泛建议过宽 0.100，对检索过严 0.133。剩下的限制是**覆盖面**——一位评审、每系统 15 条、一次坐下来——而不是「没做校验」。
* **issue 级检索指标曾是恒等式，已退役。** 原表对每个检索器都报 `recall@5 = 1.000 / MRR = 1.000 / 留一交叉 = 0.000`，29 条和 95 条都一样。两半都是构造产物：*查询是 issue 标题、每个 chunk 又带标题前缀，金标 issue 必然排第 1（实测窗口里 98–99.8% 就是金标 issue 自己的 chunk）*；而*参考文档属于金标 issue，把它移出索引后唯一相关文档按定义消失，留一交叉恒为 0*。替代指标按**回答的那条评论**打分，确实有区分度（0.516–0.621）。旧数字留在 `data/results/` 作为归档臂，不作为证据。
* **评测集是挖出来的，不是精编基准。** 维护者回复偶尔不完整，或回答的问题比标题更窄。保留/丢弃的人工复核就是为切掉这些，复核表已提交，可审计：审了 200 条候选，保留 95 条（47.5%）。
* **单一仓库、单领域。** 关于 BM25 与 dense 权重的结论是领域相关的；换一个 preset 会重排这张表。
* **标题当查询偏向字面匹配。** BM25 因此拿到稍容易的任务。有了评论级指标，这个偏差现在是**可测的**而不只是被提防，但构造一个改写查询集仍是诚实的下一步。
* **检索只支持英文。** 语料是英文 issue 文本，BM25 用英文停用词与词干，embedding 是 `bge-base-en-v1.5`——英文专用模型。用其他语言提问会被编码成噪声：检索返回无关线程，生成器随后**正确地拒答**而不是编一个答案。那个拒答行为是对的，但体验很差；更要紧的是，这是**本评测集的设计漏洞**：95 条全是英文标题，语言从来不是变量。演示页因此写了「请用英文提问」。要真正修好，要么换多语言 embedding（并重跑所有数字），要么在检索前加翻译（那会让演示页偏离被测管道——刻意没做）。
* **不做多跳。** 每个问题都从单个 issue 线程回答。需要组合两个 issue 的问题不在范围内。
* **绝对分数绑定生成器。** 仓库里跑的用的是 `--provider deepseek` 的 `deepseek-chat`；默认生成器是本地 3B，绝对分数更低。闭卷 vs RAG 的**差距**是结论，它扛得住更强的生成器；绝对数字不能迁移。
